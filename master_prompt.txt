# 1. PROBLEM STATEMENT AND PRODUCT VISION

An online seller receives refund and return requests that may be:

- **Genuine:** A legitimate refund or return request.
- **Mistaken:** An honest mistake, accidental duplicate, wrong-size selection, or genuine product issue.
- **Suspicious:** A request that exhibits concerning patterns requiring additional investigation.

Manual review is slow and costly. Simple static rules may miss coordinated behavior, while overly aggressive rules can unfairly penalize honest customers.

ReturnShield is an ML-assisted refund-risk monitoring platform that combines transaction features, customer history, real-time Redis behavioral signals, and a transparent decision policy.

## Core product workflow

A refund request enters the backend.

1. Validate the request.
2. Check idempotency and transaction state.
3. Retrieve authoritative behavioral context from Redis.
4. Construct the exact model feature vector.
5. Run the trained three-class classifier.
6. Calculate the risk score and risk tier.
7. Apply a versioned policy to recommend an action.
8. Persist the decision and evidence in MongoDB.
9. Return the structured result to the caller.
10. Publish the real event to the React dashboard.

The dashboard allows an analyst to investigate a transaction, examine the evidence, monitor system health, and control a live traffic simulation.

## Essential innovation

The key demonstration is that a request that looks ordinary in isolation may become more concerning when repeated requests or shared-device activity accumulate.

The system must prove this using real Redis state, actual API requests, model predictions, and the documented policy.

**A Suspicious prediction is not proof of fraud.** The system must support human review, avoid unsupported accusations, and never take irreversible action solely because of a model score.

# 5. EXACT MACHINE-LEARNING FEATURE CONTRACT

The model uses exactly these 12 features, in the order defined below.

| #  | Feature                    | Type and definition                                                       |
| -- | -------------------------- | ------------------------------------------------------------------------- |
| 1  | `account_age_days`         | Integer, account age at the request timestamp                             |
| 2  | `total_past_orders`        | Integer, completed orders before the current request                      |
| 3  | `historical_return_ratio`  | Float from 0 to 1, historical returns divided by eligible previous orders |
| 4  | `past_inr_claims`          | Integer, previous item-not-received or empty-box claims                   |
| 5  | `item_price`               | Float, item price in INR                                                  |
| 6  | `product_category_code`    | Integer 1 to 5                                                            |
| 7  | `return_reason_code`       | Integer 1 to 5                                                            |
| 8  | `hours_since_delivery`     | Float, delivery to refund request                                         |
| 9  | `weight_discrepancy_grams` | Nullable float, dispatch weight minus return-scan weight                  |
| 10 | `shared_identity_links`    | Integer, distinct other accounts sharing a defined identity               |
| 11 | `is_cod_order`             | Binary, 1 means cash on delivery                                          |
| 12 | `purchased_in_sale`        | Binary, 1 means purchased during a sale                                   |

## Category mappings

`product_category_code`:

- 1: Electronics
- 2: Fashion/Apparel
- 3: Footwear
- 4: Home
- 5: Books

`return_reason_code`:

- 1: Wrong Size/Fit
- 2: Not Working/Technical Issue
- 3: Empty Box/Missing Item
- 4: Physical Damage
- 5: Changed Mind

Labels:

- `0`: Genuine
- `1`: Mistaken
- `2`: Suspicious

Store this schema, category mapping, label mapping, nullability, validation rules, and schema hash alongside the trained model.

Reject incompatible model artifacts. Training and inference must use the same feature order and semantic definitions.

## 5.1 Prediction timing and leakage prevention

The initial decision occurs when a refund request is submitted.

A return-scan weight discrepancy may not yet exist. Therefore, `weight_discrepancy_grams` is nullable and training data must reproduce realistic missingness.

Never train on information that would not be available at prediction time.

Define the timestamp at which every feature becomes available. Do not allow post-decision outcomes, future events, scenario intent, or UI metadata into the model.

The optional future re-scoring of a returned item is outside the core implementation.

## 5.2 Redis and model feature consistency

The backend computes `shared_identity_links` from authoritative Redis identity relationships.

The client must never be trusted to supply this value.

The live-traffic generator may use a scenario's intended identity-sharing pattern to choose identifiers, but the API must independently calculate the actual value.

Training data must define this feature consistently with inference. If a compatible source feature is unavailable, document the mismatch and do not fabricate equivalence.

Additional Redis behavioral signals, such as recent request counts, repeated attempts, and time since the previous request, are used by the separate policy layer. They are not silently appended to the 12-feature model.

# 7. RISK SCORE AND DECISION POLICY

The model prediction and final operational action are different outputs.

## 7.1 Three separate concepts

**Model prediction:** Class probabilities for Genuine, Mistaken, and Suspicious.

**Behavioral evidence:** Actual signals calculated from Redis.

**Policy decision:** Final risk tier and recommended action after combining model output with documented behavioral rules.

Keep these separate in every API response, database record, investigation view, and report.

## 7.2 Risk score

Define a documented score from 0 to 100.

A possible starting formula is:

`base_score = 100 × (P(Suspicious) + w × P(Mistaken))`

Then apply documented, bounded Redis overlay increments and clamp the result to 0 to 100.

Choose and document `w`, the overlay rules, thresholds, and policy version.

This score is an operational risk index. Do not call it a calibrated fraud probability unless calibration has actually been assessed.

Define configurable tiers, for example:

- Low
- Elevated
- High

Map tiers to proportional recommendations:

- Routine processing.
- Additional verification.
- Human review.

Do not automatically reject every high-risk request. A model score alone is insufficient grounds for irreversible action.

Never treat COD, sale purchase, new accounts, or a product category as proof of abuse.
